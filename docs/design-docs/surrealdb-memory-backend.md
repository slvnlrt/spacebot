# SurrealDB Memory Backend

Replace the multi-engine memory persistence layer (SQLite + LanceDB) with a
single embedded **SurrealDB v3** instance that unifies the document, graph,
vector, and full-text concerns the memory subsystem currently splits across two
databases.

> Status: **design / investigation**. No production code yet. This document is
> the preliminary research and target design. Exact SurrealQL syntax and crate
> APIs must be validated against the pinned SurrealDB version during the Phase 0
> spike before any of the schema below is treated as final.

## Problem

The "memory" subsystem (`src/memory/`) is the agent's long-term + working
memory. To do hybrid recall it currently stitches **three** storage engines
together by hand:

| Engine | Crate | What it holds for memory |
| --- | --- | --- |
| **SQLite** | `sqlx` | `memories` (records), `associations` (graph edges), `working_memory_*` (temporal event log) |
| **LanceDB** | `lancedb` / `lance-index` | `memory_embeddings` — 384-dim vectors (HNSW, cosine) + full-text index (Tantivy) on `content` |
| **fastembed** | `fastembed` | Generates the 384-dim embeddings (`all-MiniLM-L6-v2`) |

This split has real costs:

1. **The graph is simulated in SQL.** Associations are an edge table and
   traversal is a hand-written BFS in `search.rs::traverse_graph` that issues
   one query per node, loads each memory individually, and tracks `visited` in
   Rust. It cannot be expressed as a single query.
2. **Hybrid search is glued in application code.** `hybrid_search` runs three
   independent queries (vector via Lance, FTS via Lance, graph via SQLite),
   pulls everything into memory, then fuses with Reciprocal Rank Fusion (RRF) in
   Rust. The content lives in Lance *and* the metadata lives in SQLite, so every
   vector/FTS hit triggers a second `store.load(id)` round-trip to SQLite.
3. **Two sources of truth that can drift.** `content` is duplicated into Lance
   for FTS; embeddings can desync from `memories`. `lance.rs` already has a
   whole "table is corrupted, drop and rebuild from SQLite" recovery path
   because the two stores have no shared transaction.
4. **No abstraction layer.** `MemoryStore` wraps `SqlitePool`, `EmbeddingTable`
   wraps `lancedb::Table`, both directly. There is no `MemoryBackend` trait, so
   the engines are wired straight into `store.rs`, `lance.rs`, `search.rs`,
   `maintenance.rs`, and `working.rs`.

SurrealDB collapses document + graph + vector + full-text into one engine with a
single query language and one ACID transaction boundary — which is exactly the
shape of this subsystem.

## Why SurrealDB (and what it does *not* do)

What it replaces here:

- **Graph natively.** `associations` become first-class `RELATE` edges.
  Traversal (`->relates->memory`) happens *inside* a query, at any depth,
  removing the Rust BFS entirely.
- **Vector natively.** Native **HNSW** index (`DIST COSINE`, `TYPE F32`), KNN
  via the `<|K|>` operator — replaces LanceDB.
- **Full-text natively.** `DEFINE ANALYZER` + `FULLTEXT` index with BM25 —
  replaces the Lance/Tantivy FTS.
- **One record, one transaction.** Metadata, embedding, and content live on the
  *same* `memory` record. No more `store.load(id)` after every vector hit, no
  duplicated `content`, no drift-recovery path.
- **Embedded / in-process.** The `surrealdb` crate runs embedded against
  **SurrealKV** (or RocksDB) on local disk — same single-machine, file-backed
  deployment model as the current SQLite + Lance dirs. No server to run.

What it explicitly does **not** do:

- **It does not generate embeddings.** SurrealDB stores and indexes vectors but
  does not compute them ("embeddings are not generated by the database" — it
  even points users at FastEmbed). **`fastembed` and `embedding.rs` stay as-is.**

## Scope

**In scope** — the per-agent memory subsystem only:

- `memories` + `associations` + `memory_embeddings` → one SurrealDB `memory`
  table + `relates` edges.
- Optionally the `working_memory_*` tables (Phase 4 — lower priority, no vector
  or graph needs, currently pure SQLite).

**Out of scope** — SQLite stays the backend for everything else. SQLite is not
"the memory database"; it is the app database. The instance DB
(`tasks`, `projects`, `repos`, `worktrees`) and the per-agent
conversation/channel tables are **not** touched. SurrealDB is added *alongside*
SQLite as a memory-scoped store, not a global replacement.

This keeps the change confined to `src/memory/` plus the wiring in `db.rs` and
the two construction sites.

## Current data model (what we must reproduce)

### `memories` (SQLite) → maps to fields in `types.rs::Memory`

`id` (uuid text, PK), `content`, `memory_type` (8-variant enum),
`importance` f32, `created_at`/`updated_at`/`last_accessed_at`, `access_count`,
`source?`, `channel_id?`, `forgotten` (soft-delete).

### `associations` (SQLite) → `types.rs::Association`

`id`, `source_id`, `target_id`, `relation_type` (6-variant enum:
`related_to`/`updates`/`contradicts`/`caused_by`/`result_of`/`part_of`),
`weight` f32, `created_at`. Unique on `(source_id, target_id, relation_type)`,
`ON DELETE CASCADE` from `memories`.

### `memory_embeddings` (LanceDB)

`id` (text), `content` (text, for FTS), `embedding` (FixedSizeList<f32>[384]).
HNSW index on `embedding` (cosine), FTS index on `content`.

### Behaviours that must survive the port

- **Hybrid search** (`search.rs`): RRF over vector + FTS + graph; graph seeds are
  `importance >= 0.8` memories whose content keyword-matches the query; graph
  scoring uses per-relation-type multipliers (`updates` 1.5, `caused_by`/
  `result_of` 1.3, `related_to` 1.0, `part_of` 0.8, `contradicts` 0.5); only
  `related_to`/`part_of` edges are followed deeper (default depth 2).
- **Non-hybrid modes**: `Recent` / `Important` / `Typed` are plain metadata
  queries with sorts (`created_at`, `importance`, `access_count`).
- **Maintenance** (`maintenance.rs`): importance decay with access boosts;
  prune low-importance memories older than N days; merge near-duplicates
  (similarity > 0.95) — combine content, **rewire associations**, soft-delete the
  loser. The merge is a multi-statement atomic operation today.
- **`forgotten`** memories are excluded from search/recall but retained.
- `find_similar(memory_id, threshold, limit)` — KNN from an existing memory's
  own embedding, excluding itself.

## Target SurrealDB schema (draft)

> All SurrealQL below is the **intended** target and must be validated against
> the pinned SurrealDB version during Phase 0. Syntax notes are based on
> SurrealDB v3 docs (HNSW index params, `FULLTEXT` analyzer since 3.0-beta).

```surql
-- Namespace/database selected at connect time (e.g. ns=spacebot, db=<agent_id>).

DEFINE TABLE memory SCHEMAFULL;
DEFINE FIELD content          ON memory TYPE string;
DEFINE FIELD memory_type      ON memory TYPE string
  ASSERT $value IN ['fact','preference','decision','identity',
                    'event','observation','goal','todo'];
DEFINE FIELD importance       ON memory TYPE float DEFAULT 0.5;
DEFINE FIELD created_at       ON memory TYPE datetime DEFAULT time::now();
DEFINE FIELD updated_at       ON memory TYPE datetime DEFAULT time::now();
DEFINE FIELD last_accessed_at ON memory TYPE datetime DEFAULT time::now();
DEFINE FIELD access_count     ON memory TYPE int DEFAULT 0;
DEFINE FIELD source           ON memory TYPE option<string>;
DEFINE FIELD channel_id       ON memory TYPE option<string>;
DEFINE FIELD forgotten        ON memory TYPE bool DEFAULT false;
DEFINE FIELD embedding        ON memory TYPE option<array<float>>;

-- Vector index (replaces LanceDB HNSW). 384 = all-MiniLM-L6-v2.
DEFINE INDEX memory_embedding_hnsw ON memory FIELDS embedding
  HNSW DIMENSION 384 DIST COSINE TYPE F32;

-- Full-text index (replaces Lance/Tantivy FTS).
DEFINE ANALYZER memory_analyzer TOKENIZERS class FILTERS lowercase, ascii;
DEFINE INDEX memory_content_fts ON memory FIELDS content
  FULLTEXT ANALYZER memory_analyzer BM25;

-- Metadata indexes for the non-hybrid modes.
DEFINE INDEX memory_type_idx       ON memory FIELDS memory_type;
DEFINE INDEX memory_importance_idx ON memory FIELDS importance;

-- Associations become graph edges (replaces the associations table).
-- Edge table `relates`: memory -> relates -> memory.
DEFINE TABLE relates SCHEMAFULL TYPE RELATION FROM memory TO memory;
DEFINE FIELD relation_type ON relates TYPE string;
DEFINE FIELD weight        ON relates TYPE float DEFAULT 0.5;
DEFINE FIELD created_at    ON relates TYPE datetime DEFAULT time::now();
DEFINE INDEX relates_unique ON relates
  FIELDS in, out, relation_type UNIQUE;
```

### Record IDs

Keep the existing UUID strings to make migration a 1:1 copy and to keep the
public API/`types.rs` unchanged: `memory:⟨'…uuid…'⟩`. The `id` field exposed in
`Memory` is the UUID string; the SurrealDB Thing id wraps it.

## Query mapping

### Create a memory (+ embedding, in one statement)

```surql
CREATE memory:$id SET
  content = $content, memory_type = $type, importance = $importance,
  source = $source, channel_id = $channel_id, embedding = $embedding;
```

### Create an association

```surql
RELATE memory:$source->relates->memory:$target
  SET relation_type = $relation_type, weight = $weight;
```

### Vector KNN (replaces `EmbeddingTable::vector_search`)

```surql
SELECT id, content, importance, memory_type,
       vector::distance::knn() AS distance
FROM memory
WHERE embedding <|$k|> $query_embedding
  AND forgotten = false;
```

### Full-text (replaces `EmbeddingTable::text_search`)

```surql
SELECT id, search::score(0) AS score
FROM memory
WHERE content @0@ $query AND forgotten = false
ORDER BY score DESC LIMIT $k;
```

### Graph traversal (replaces `search.rs::traverse_graph` BFS)

```surql
-- depth-2 expansion from seed ids, following related_to/part_of, in ONE query:
SELECT id, content, importance,
       ->relates.{relation_type, weight} AS edges,
       ->relates->memory AS related
FROM $seed_ids
WHERE forgotten = false;
```

The per-relation-type score multipliers and the depth-2 "only follow
related_to/part_of" rule can stay in Rust (cheap, already tested) operating on
the returned edge metadata, **or** be pushed into SurrealQL. Decide in Phase 2.

### The end goal: hybrid in (close to) one round-trip

RRF itself stays in Rust (it is pure, well-tested, and trivial). The win is that
each source becomes one SurrealDB query returning the full memory record — no
per-hit `store.load(id)` back to a second database, no `content` duplication.
A later optimisation can fuse vector+FTS+graph into a single multi-statement
SurrealQL transaction.

## Rust integration points

Files that change, and how:

| File | Change |
| --- | --- |
| `src/db.rs` | Add a `surreal: Surreal<Db>` handle to the `Db` bundle; open embedded SurrealKV at `data_dir/surreal`; run schema definition (idempotent `DEFINE ... IF NOT EXISTS`). Keep `sqlite`, drop `lance` once Phase 3 lands. |
| `src/memory/store.rs` | Re-implement CRUD + association ops against SurrealDB. `types.rs` structs stay; (de)serialise via `serde`. |
| `src/memory/lance.rs` | **Removed** — vector + FTS fold into `store.rs`/the `memory` table. |
| `src/memory/embedding.rs` | **Unchanged** — fastembed stays. |
| `src/memory/search.rs` | `hybrid_search` issues SurrealQL for vector/FTS/graph; keep RRF + multipliers; drop the SQLite-load round-trips. |
| `src/memory/maintenance.rs` | Decay/prune/merge as SurrealQL; the atomic merge becomes a single transaction. |
| `src/memory/working.rs` | Phase 4 (optional); SQLite-backed until then. |
| `src/main.rs` (~2890), `src/api/agents.rs` (~834) | Construction sites: build stores from the `surreal` handle instead of `db.lance`. |
| `Cargo.toml` | Add `surrealdb = { version = "3", features = ["kv-surrealkv"] }`; remove `lancedb`, `lance-index`, and the Arrow deps once Phase 3 lands. |
| `migrations/` | SurrealDB schema is applied in-code (not via `sqlx::migrate!`). The SQLite memory migrations stay only until the cutover, then become historical. |

### Embedded init sketch

```rust
use surrealdb::engine::local::SurrealKv; // feature = "kv-surrealkv"
use surrealdb::Surreal;

let surreal = Surreal::new::<SurrealKv>(data_dir.join("surreal")).await?;
surreal.use_ns("spacebot").use_db(agent_id).await?;
surreal.query(SCHEMA_SURQL).await?; // idempotent DEFINEs
```

## Migration of existing data

Per agent, one-time, idempotent:

1. Read all rows from SQLite `memories` + `associations`, and all vectors from
   Lance `memory_embeddings`.
2. For each memory, `CREATE memory:⟨uuid⟩ SET … embedding = ⟨vec⟩`.
3. For each association, `RELATE` the edge.
4. Verify counts; on success, mark migrated (a sentinel key in redb or a marker
   file) so it runs once.
5. Leave the old `agent.db`/`lancedb` in place for one release as a rollback
   path; remove in a follow-up.

A `--reindex` path already exists conceptually (Lance rebuilds embeddings from
SQLite); the migration can reuse fastembed to regenerate any missing vectors.

## Phased plan

- **Phase 0 — Spike (1–2 days).** Add `surrealdb` behind a feature flag. Stand up
  the embedded SurrealKV instance, apply the schema, and validate the four
  primitives on real-ish data: insert, KNN, FTS, `RELATE`+traversal. **Confirm
  HNSW + `forgotten = false` filter behaves** (there are reports of HNSW
  returning all rows when combined with filters — must verify with our volume).
  Output: a throwaway test + a go/no-go note appended here.
- **Phase 1 — Store.** Port `store.rs` CRUD + associations; keep `types.rs`.
  Dual-run against the SQLite impl in tests to prove parity.
- **Phase 2 — Search.** Port `hybrid_search` (vector/FTS/graph) + non-hybrid
  modes; keep RRF and the relation multipliers; assert the existing
  `search.rs` tests pass.
- **Phase 3 — Maintenance + cutover.** Port decay/prune/merge; migrate data;
  remove `lance.rs`, the LanceDB/Arrow deps, and the SQLite memory tables from
  the hot path.
- **Phase 4 — (optional) Working memory.** Move `working_memory_*` to SurrealDB
  for a fully unified memory store, or leave on SQLite.

Each phase is independently shippable behind the feature flag; `main` keeps the
SQLite+Lance path until Phase 3 flips the default.

## Risks and open questions

- **HNSW maturity / filtered KNN.** The single biggest unknown. Must be settled
  in Phase 0 (perf at our scale, correctness of `<|K|>` + `WHERE forgotten`).
  Fallback: brute-force/MTREE, or keep Lance for vectors only (smaller win).
- **Loss of compile-time-checked queries.** `sqlx::query!` is verified at build;
  SurrealQL is runtime strings. Mitigate with a thin query module + integration
  tests.
- **Build weight & footprint.** `surrealdb` is a heavy dependency. We do remove
  `lancedb` + `lance-index` + Arrow in exchange, so net dependency weight may
  improve — measure.
- **Embedding generation stays external.** No change to fastembed; SurrealDB is
  storage/index only. (Documented here so it isn't mistaken for a feature.)
- **Per-agent database model.** Today each agent has its own `agent.db` + Lance
  dir. Map this to a SurrealDB **database** per agent under one namespace, or one
  embedded instance per agent. Decide in Phase 0.
- **Two engines during transition.** SQLite still backs conversations/tasks, so
  the process runs SQLite *and* SurrealDB concurrently until/unless more is
  migrated. Acceptable; just noted.
- **Kodex reference.** The owner's `Kodex` project reportedly integrates
  SurrealDB for exactly these memory/graph/embedding use cases. It was not
  accessible from this session (private). Before Phase 1, mine it for its
  SurrealDB data model, KNN+graph query patterns, and embedded-init code so this
  port mirrors a known-good integration instead of re-deriving conventions.
