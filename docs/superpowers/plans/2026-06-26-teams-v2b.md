# Teams Adapter v2b Implementation Plan — Card-Button Interactions

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a Teams agent send Adaptive Card buttons and receive the click back as a `MessageContent::Interaction`, completing the conversational-interaction loop on the existing v2a card path.

**Architecture:** Two additive arms in `src/messaging/teams.rs`, both onto vocabulary that already exists end-to-end. Outbound: render `OutboundResponse::RichMessage.interactive_elements` (today ignored) as Adaptive Card `actions` (`Action.Submit` for clickable buttons, `Action.OpenUrl` for link buttons), embedding a correlation id in each Submit's `data`. Inbound: a Teams `Action.Submit` click arrives as a `message` Activity carrying a `value` object (the button `data` merged with any input values) — map it to `MessageContent::Interaction` (same rail as Slack `block_actions` / Discord component clicks). No new core vocabulary; no `agent/` changes.

**Tech Stack:** Rust, `serde_json` (Adaptive Card actions + inbound `value`), the v2a send seam (`send_activity`/`build_message_body`/`cards_to_attachments`). `axum`/`reqwest`/`jsonwebtoken` unchanged.

## Global Constraints

- **`src/messaging/teams.rs` ONLY.** No changes to `src/agent/`, `src/lib.rs` types, `src/main.rs`, or config. No new `MessageContent`/`OutboundResponse`/`StatusUpdate` variant — consume the existing ones.
- **Builds on v2a (HEAD `f2c0ead9`).** Reuse, do not duplicate: `card_to_adaptive`/`cards_to_attachments` (Adaptive Card emit), `build_message_body(text, attachments, reply_to)`, `send_activity`. The Adaptive Card envelope/version is already fixed: `$schema="http://adaptivecards.io/schemas/adaptive-card.json"`, `version="1.5"`, `type="AdaptiveCard"`, attachment `contentType="application/vnd.microsoft.card.adaptive"`.
- **Consumes `cards` + now `interactive_elements`; still IGNORES `blocks` and `poll`** (mirror how each adapter ignores the others' payloads). Plain-text / cards-only behavior from v2a is unchanged.
- **`Interaction` is flattened to text for the agent** (`agent/channel.rs` renders it via `Display`) — this is fine for conversational buttons (the agent reacts in conversation), but it is NOT a deterministic security gate. Any approval-gating use is v3, not v2b. Document this in code.
- **Inbound interaction must still pass the existing gates:** the v1 inbound chain (JWT validate → parse → serviceUrl capture → permission filter → dispatch) is unchanged; a click is a normal inbound `message` Activity subject to the same `TeamsPermissions::is_allowed`.
- **Tests:** `cargo test --lib` stays green (baseline 959/0 at `f2c0ead9`). Heavy cargo wrapped: `systemd-run --scope -p MemoryMax=40G -p MemorySwapMax=0 cargo …`. Disk guard blocks builds under 25 GiB free (currently ~77 GiB).
- **Commits:** match the branch's **trailer-free** style (verify `git log -1 --format=%B | grep -ciE "Co-Authored-By|Claude-Session|Generated with"` == 0). One commit per task. **Do not push.**

## Scope & deliberate deferrals (read before implementing)

v2b as designed in `teams-roadmap.md` nominally bundled three things; this plan implements **only card-button interactions** and explicitly scopes out the other two, for reasons that hold until a real-Teams test is available:

- **Thread replies — already satisfied, no code.** Teams threads are addressed by `conversation.id` itself: a channel message in a thread carries `…@thread.tacv2;messageid=<root>` in its conversation id, and `respond`/`send_activity` already POST back to that exact id (and forward `reply_to_id` from `teams_reply_to_id`). So replies already land in the originating thread. The `OutboundResponse::ThreadReply { thread_name }` "named new thread" concept (Discord-style) has no Bot Framework equivalent — bots cannot name channel threads. The current `ThreadReply` arm already degrades correctly (sends the text, threaded via `reply_to_id`). **Action: a one-line doc/code comment only (Task 3); no behavioral change. Revisit only if a real-Teams test shows a threading gap.**
- **Outbound reactions — deferred (separate subsystem).** Adding/removing a reaction to a Teams message is **not** part of the Bot Connector REST API the adapter speaks; it requires Microsoft Graph with a different auth scope (`ChannelMessage.*`) and app-permission consent — a distinct integration, not an additive `respond` arm. Inbound reactions (`messageReaction` activities) also have **no** `MessageContent` variant to map onto. Low ROI, cannot be validated blind. **Action: keep the current `Reaction`/`RemoveReaction` no-op; record the deferral in `teams-roadmap.md` (Task 3).**
- **Select menus (`InteractiveElements::Select`) — deferred within interactions.** Buttons cover the high-value cases (approve/reject, quick replies). A Teams `Input.ChoiceSet` + submit is doable but adds body/input correlation that is better validated against a real client. This plan renders **buttons**; `Select` is left as a documented no-op arm (Task 1) so it compiles and is obvious where to extend.

- Consumes: `crate::Button` (lib.rs:982 — `label: String`, `custom_id: Option<String>`, `style: ButtonStyle`, `url: Option<String>`); `crate::ButtonStyle` (Primary/Secondary/Success/Danger/Link); `crate::InteractiveElements` (lib.rs:975 — `Buttons { buttons: Vec<Button> }` / `Select { select: SelectMenu }`); v2a `cards_to_attachments`, `build_message_body`, `send_activity`.
- Produces: `fn button_to_action(btn: &crate::Button) -> serde_json::Value`; `fn interactive_elements_to_actions(elems: &[crate::InteractiveElements]) -> Vec<serde_json::Value>`; `fn actions_card_attachment(text: &str, actions: Vec<serde_json::Value>) -> serde_json::Value`.

**Mapping decisions:**
- A button with `url: Some(u)` → `{"type":"Action.OpenUrl","title":label,"url":u}` (regardless of style — a URL button is a link).
- Otherwise → `{"type":"Action.Submit","title":label,"data":{"action_id":<id>,"label":label}}` where `<id> = custom_id.clone().unwrap_or_else(|| label.clone())`. The `data` object is exactly what Teams echoes back as the inbound `value` (Bot Framework merges `Action.Submit.data` + any input values), so embedding `action_id`+`label` gives a clean inbound round-trip.
- `ButtonStyle` has no portable Adaptive Card equivalent (Adaptive Card action styles are limited/host-specific); omit it — documented in a comment. (Do not invent a mapping.)
- `InteractiveElements::Select` → render nothing yet (return no actions for that element) with a `// TODO(v2b.select)` comment — deferred per Scope section.
- The actions attach to a dedicated Adaptive Card appended **after** any `cards` attachments: `actions_card_attachment(text, actions)` builds `{contentType: adaptive, content: {envelope, body:[TextBlock(text)] if text non-empty else [], actions}}`. Appended only when there is at least one action.

```rust
/// Convert a generic `Button` to an Adaptive Card action.
///
/// A button with a `url` becomes `Action.OpenUrl`; otherwise `Action.Submit`
/// whose `data` (echoed back by Teams as the inbound `value`) carries the
/// correlation `action_id` (the button's `custom_id`, or its label as a
/// fallback) plus the human `label`. `ButtonStyle` has no portable Adaptive
/// Card equivalent and is intentionally dropped.
fn button_to_action(btn: &crate::Button) -> serde_json::Value {
    if let Some(url) = &btn.url {
        return serde_json::json!({
            "type": "Action.OpenUrl",
            "title": btn.label,
            "url": url,
        });
    }
    let action_id = btn.custom_id.clone().unwrap_or_else(|| btn.label.clone());
    serde_json::json!({
        "type": "Action.Submit",
        "title": btn.label,
        "data": { "action_id": action_id, "label": btn.label },
    })
}

/// Flatten `interactive_elements` into Adaptive Card actions.
///
/// Renders `Buttons`; `Select` (Adaptive Card `Input.ChoiceSet`) is deferred
/// (see the v2b plan Scope section) and contributes no actions yet.
fn interactive_elements_to_actions(
    elems: &[crate::InteractiveElements],
) -> Vec<serde_json::Value> {
    let mut actions = Vec::new();
    for elem in elems {
        match elem {
            crate::InteractiveElements::Buttons { buttons } => {
                actions.extend(buttons.iter().map(button_to_action));
            }
            // TODO(v2b.select): render SelectMenu as an Input.ChoiceSet + a
            // single Action.Submit once validated against a real Teams client.
            crate::InteractiveElements::Select { .. } => {}
        }
    }
    actions
}

/// Build a standalone Adaptive Card attachment carrying `text` (if any) and
/// the given `actions`. Appended after content cards so buttons render below.
fn actions_card_attachment(text: &str, actions: Vec<serde_json::Value>) -> serde_json::Value {
    let mut body: Vec<serde_json::Value> = Vec::new();
    if !text.is_empty() {
        body.push(serde_json::json!({ "type": "TextBlock", "text": text, "wrap": true }));
    }
    serde_json::json!({
        "contentType": "application/vnd.microsoft.card.adaptive",
        "content": {
            "$schema": "http://adaptivecards.io/schemas/adaptive-card.json",
            "type": "AdaptiveCard",
            "version": "1.5",
            "body": body,
            "actions": actions
        }
    })
}
```

```rust
/// Map an `Action.Submit` `value` object to a `MessageContent::Interaction`.
///
/// `value` is the button `data` (we embed `action_id`+`label`) merged with any
/// Adaptive Card input submissions. NOTE: downstream the agent sees this
/// flattened to text (channel.rs renders Interaction via Display) — fine for
/// conversational buttons, but NOT a deterministic gate (that is v3).
fn value_to_interaction(
    value: &serde_json::Value,
    message_ts: Option<String>,
) -> crate::MessageContent {
    let action_id = value
        .get("action_id")
        .and_then(|v| v.as_str())
        .unwrap_or("")
        .to_string();
    let label = value.get("label").and_then(|v| v.as_str()).map(|s| s.to_string());
    // Any other string-valued fields are submitted input values.
    let values: Vec<String> = value
        .as_object()
        .map(|obj| {
            obj.iter()
                .filter(|(k, _)| k.as_str() != "action_id" && k.as_str() != "label")
                .filter_map(|(_, v)| v.as_str().map(|s| s.to_string()))
                .collect()
        })
        .unwrap_or_default();
    crate::MessageContent::Interaction {
        action_id,
        block_id: None,
        values,
        label,
        message_ts,
    }
}
```
